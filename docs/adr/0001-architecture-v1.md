# ADR-0001: Architecture V1

- Status: proposed (draft from plan V1)
- Date: 2026-11-12

## Decision

- Modular Rust monolith exposing REST `/api/v1` and MCP (`rmcp`, Streamable HTTP plus a stdio bridge) from a single binary.
- Generic SQLx repository over PostgreSQL and SQLite, with mirrored migrations.
- Connectors are crates depending only on `connector-sdk` (dependencies allow-listed, `cargo vet`). 2FA goes through an `Interaction` callback reserved to user-triggered jobs; scheduled and MCP jobs are strictly `Unattended`.
- Idempotence by `remote_id` + `occurrence_index`; approximate matching only when the user manually changes an account's source.
- The sync source is chosen by the user for each bank (direct connector or Enable Banking), with no automatic failover. A broken connector triggers a notification and a proposal to use Enable Banking. Enable Banking ships before the direct connectors.
- Secrets live behind `sync` only (`api`/`mcp` use `sync-facade`, with no `secrets` in their closure). AES-256-GCM with a KEK and AAD. The master key is generated by an init container into a separate `em-keys` volume (never printed) or supplied by the admin; OS keychain on desktop.
- Money as `i64` minor units plus `Decimal`.
- One React SPA reused by Tauri; local desktop mode uses a URI scheme into the Axum `Router` (hardened loopback fallback).

## Drivers

- Credential security and intra-household privacy.
- Maintainability by a single maintainer.
- Server/desktop and Postgres/SQLite parity.
- User control over the connection method.

## Alternatives considered

`sqlx::Any`, double `query!`, SQLite only, SeaORM (plan B); SvelteKit, Solid; 2FA state machine, out-of-process connectors; per-credential DEKs; key auto-generation in the data volume, passphrase at every start; hand-rolled or external MCP; `i64` or `Decimal` everywhere; loopback HTTP or Tauri IPC commands; parallel direct+EB sync; automatic failover to Enable Banking (rejected: user decision); key supplied only by the admin (rejected: `docker compose up` must work in one command).

## Why this choice

Minimise duplicated code (one query set, one HTTP facade, one connector trait) while making security guarantees verifiable in CI (dependency closure, separate `SyncTrigger`/`CredentialIntake`/`ChallengeIntake` traits, canary tests, OTP counter). Honour the user's decisions on key generation and source choice. Tackle external uncertainties (banks, Enable Banking, desktop transport) first and report honestly: a no-go means the acceptance criterion is not met.

## Consequences

Positive: a single code path; contributors isolated from the core; no unsolicited OTP.

Negative:
- The master key is in process memory: the crate boundary is compile-time hygiene against accidental leaks, not isolation against a compromised process.
- No compile-time SQL checking; two migration folders.
- A 2FA login cannot resume after a restart.
- The MCP SDK is young.
- Local desktop syncs only while the app runs; the transport uses polling, no SSE.
- Losing the key forces re-entering credentials.
- Without automatic failover, data for an account with a broken connector stays stale until the user acts.
- Key and data share a host in the default deployment (back up the exported key separately).
